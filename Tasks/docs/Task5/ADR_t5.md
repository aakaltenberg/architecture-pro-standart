### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность сервиса кредитных заявок — 99.9% (24/7), с переключением на резервный ЦОД. |
| 2 | Горизонтальное масштабирование нового сервиса кредитных заявок для выдерживания пиковых нагрузок. Целевой показатель - 5000 RPS |
| 3 | Запрет прямого доступа интернет-банка и сайта к БД АБС; использование промежуточных сервисов и очередей. |
| 4 | Circuit Breaker для вызовов внешних систем (скоринг, БКИ, СМС-шлюз). |
| 5 | Время отклика интерфейса при подаче заявки — не более 2 секунд; для предодобренных предложений — 300 мс. |
| 6 | Использовать существующие технологии банка: Java, Python, MS SQL, Oracle. |
| 7 | Избегать доработок ядра интернет-банка и Кредитного конвейера силами подрядчика. |
| 8 | Чувствительные данные (паспорт, ФИО) передавать только по HTTPS/TLS и хранить в зашифрованном виде. |
| 9 | Система скоринга не должна нагружаться дополнительными предрасчётами; предодобренные предложения формируются асинхронно в периоды низкой нагрузки. |
| 10 | Обход ограничения пакетной передачи АБС ↔ Кредитный конвейер для ускорения обработки онлайн-заявок. |

### <a name="_qmphm5d6rvi3"></a>**Решение**

1. Выделение отдельного сервиса кредитных заявок (credit-service). Аналогично депозитному сервису, это позволяет изолировать новую функциональность от монолитных систем (интернет-банк, АБС) и масштабировать её независимо. Сервис реализуется на Java Spring Boot, используя существующую экспертизу команды (Java-стек уже применяется в системе кол-центра и кредитном конвейере)
2. Прямая интеграция с системой скоринга и БКИ. Для мгновенного решения по заявке с сайта необходимо выполнить скоринг в реальном времени. Система скоринга предоставляет REST API, что позволяет быстро интегрироваться. Предодобренные предложения для интернет-банка рассчитываются асинхронно (например, ночью) и сохраняются в кэше (Redis), чтобы не нагружать скоринг в пиковые часы.
3. Обход ограничения передачи АБС ↔ Кредитный конвейер раз в сутки. Существующая интеграция между АБС и конвейером работает раз в сутки и не может быть ускорена. Поэтому онлайн-заявки не должны проходить через этот канал на этапе подачи. Вместо этого сервис кредитных заявок напрямую вызывает API скоринга и, при необходимости, отправляет заявку в Кредитный конвейер для ручной обработки (если решение не может быть принято автоматически). Для стандартных заявок бэк-офис продолжает работать в конвейере. Для отображения заявки менеджеру в отделении сервис асинхронно отправляет данные в АБС через шлюз (Kafka + PL/SQL). Это гарантирует появление заявки в АБС в течение нескольких секунд, что достаточно для визита клиента.
4. Интеграция с интернет-банком и сайтом. Сайт и интернет-банк обращаются к сервису кредитных заявок по REST API. Это позволяет не вносить существенных изменений в их ядро (только добавить новые эндпоинты). Для подтверждения операций используется существующий СМС-шлюз, вызов которого инициирует сервис кредитных заявок.
5. Хранение предодобренных предложений. Для быстрого отображения в интернет-банке используется Distributed-кэш Redis. Периодический расчёт выполняется отдельным потоком в сервисе в часы низкой нагрузки, что защищает систему скоринга от перегрузки.
6. Отказоустойчивость и масштабирование. Сервис кредитных заявок выделен в отдельный сервис, который может быть горизонтально масштабируем. Для взаимодействия с внешними системами (скоринг, БКИ) применяется паттерн Circuit Breaker, чтобы изолировать сбои.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Реализовать логику кредитных заявок внутри интернет-банка. Привело бы к разрастанию монолита, зависимости от подрядчика, сложностям с масштабированием и нарушению запрета прямого доступа к БД АБС.
2. Использовать существующую интеграцию АБС → Кредитный конвейер для онлайн-заявок. Невозможно из-за ограничения на передачу раз в сутки, что не соответствует требованию обработки в течение дня.
3. Передавать заявки напрямую в Кредитный конвейер, минуя сервис кредитных заявок. Конвейер оптимизирован для внутренней обработки бэк-офисом, не имеет публичного API с нужным уровнем безопасности и не рассчитан на прямой вызов из интернет-банка. Сервис выступает защитным слоем.
4. Хранить предодобренные предложения в скоринге. Система скоринга уже испытывает пиковые нагрузки, добавление хранилища предложений усложнит её и увеличит нагрузку.
5. Использовать вместо Redis локальное хранение в отдельной таблице/схеме MS SQL. Redis быстрее.
6. Отказаться от асинхронной отправки в АБС и делать синхронный REST-вызов. АБС не готова к синхронной высокой нагрузке; асинхронный подход через Kafka буферизует запросы и защищает АБС.


**Недостатки, ограничения, риски**

1. Дополнительная сложность из-за нового сервиса и интеграций. 
2. Необходимость доработки АБС для приёма заявок через шлюз (аналогичные доработки запланированы в рамках онлайн-депозитов).
3. Задержка при отображении заявки в АБС (асинхронность). Для MVP допустима задержка в несколько секунд. В будущем можно рассмотреть синхронный API с жёстким rate limiting.
4. Отсутствие у команды опыта работы с Redis. 
5. Сложность синхронизации статусов заявки между сервисом, конвейером и АБС. Решается хорошей проработкой state-machine.
