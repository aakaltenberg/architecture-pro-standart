### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность сервисов интернет-банка — 99.9% (24/7), с переключением на резервный ЦОД при сбое. |
| 2 | Горизонтальное масштабирование новых компонентов для выдерживания роста нагрузки, целевой показатель - 5000 RPS. |
| 3 | АБС не должна быть перегружена прямыми онлайн-запросами; использовать промежуточные сервисы, очереди, кэш. |
| 4 | Circuit Breaker для вызовов внешних систем (СМС-шлюз, в будущем – БКИ, скоринг). |
| 5 | Время отклика интерфейса – миллисекунды; быстрая загрузка справочных данных (кэширование). |
| 6 | Использовать преимущественно существующие технологии банка: MS SQL, Oracle, Java, Python, .NET. |
| 7 | Избегать доработок ядра интернет-банка и системы кол-центра силами подрядчика. |
| 8 | Чувствительные данные передавать только по HTTPS/TLS, хранить персональные данные в зашифрованном виде. |
| 9 | Запрет прямого доступа интернет-банка к БД АБС для нового функционала. |

### <a name="_qmphm5d6rvi3"></a>**Решение**
1. В рамках архитектурного решения была предложена интеграция между сайтом и системой бэкэнд кол-центра. Интеграция предлагается с помощью Rest API на базе текущего бэкенд-приложения кол-центра. У команды банка есть опыт работы с Java, поэтому данную работу можно будет выполнить без привлечения подрядчика. Сервис является горизонтально масштабируемым, поэтому проблем при возрастающей нагрузке быть так не должно.

2. В рамках архитектурного решения была предложена интеграция между кол-центром и системой АБС. Ранее интеграция между двумя этими системами уже была, но не было указано каким образом было реализовано это взаимодействие (вероятно, DB to DB, либо API, который дальше шел в Oracle АБС). В текущей реализации предлагается на стороне кол-центра реализовать сервис, который будет передавать сообщения в Kafka, развернутую на стороне АБС (либо поток, проходящий через ранее реализованый API уже на стороне АБС, перенаправить в кафку)

3. В рамках архитектурного решения была предложена интеграция между интернет-банком и системой АБС. Интеграция выбрана асинхронная, интернет-банк создает сообщения, передает их в кафку, развернутую в АБС.

4. В рамках архитектурного решения было предложено сохранять все необходимые справочники в локальное хранилище интернет-банка MS SQL, а также хранить самые горячие справочные данные в кэше InProcess сервиса депозитных заявок. Обновления локального хранилища производить раз в какой-то период.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. В качестве альтернативного решения в дальнейшем для кэширования справочников можно перейти на использование DistributedMemory - Redis. Сейчас команды не знакомы с данной технологией.
2. Использование REST API напрямую из интернет-банка в АБС	АБС не имеет публичного API, способного выдержать пиковые нагрузки. Команда АБС предупредила о риске деградации.
3. Полный отказ от Kafka и использование БД как очереди	Приведёт к дополнительной нагрузке на Oracle и усложнит масштабирование.

**Недостатки, ограничения, риски**

1. Дополнительная сложность из-за введения нового сервиса и Kafka. Отсутствие у команды компетенций по Kafka.
2. Задержка между подачей заявки и её появлением в АБС (асинхронность)
3. Необходимость доработки АБС для чтения из Kafka
4. Вертикальное масштабирование АБС остаётся узким местом
