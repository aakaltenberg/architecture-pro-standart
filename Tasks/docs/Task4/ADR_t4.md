### <a name="_b7urdng99y53"></a>**Название задачи:** MVP Архитектура передачи актуальных ставок по депозитам в кол-центр и партнёрский кол-центр

### <a name="_uanumrh8zrui"></a>**Дата:** 11.04.2026
### <a name="_3bfxc9a45514"></a>**Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Сотрудник кол-центра, Система кол-центра | Просмотр актуальных ставок по депозитам | Сотрудник кол-центра через интерфейс своей системы видит текущие ставки по всем депозитным продуктам для консультации клиентов. |
| 2 | Система кол-центра, Сервис депозитных ставок | Получение ставок из централизованного источника | Система кол-центра регулярно (или по запросу) получает актуальные ставки из сервиса депозитных ставок (deposit-service) через REST API. |
| 3 | Партнёрский кол-центр, SFTP-сервер банка | Получение файла со ставками | Партнёрский кол-центр забирает с SFTP-сервера банка файл (например, CSV/XML) с актуальными ставками для консультации клиентов. |
| 4 | Сервис депозитных ставок, SFTP-сервер | Генерация и выгрузка файла ставок | Сервис депозитных ставок с заданной периодичностью формирует файл с актуальными ставками и размещает его на SFTP-сервере банка. |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Актуальность ставок: данные должны обновляться не реже одного раза в сутки (для партнёра) и в режиме реального времени (для внутреннего кол-центра). |
| 2 | Безопасность: передача файлов по SFTP должна использовать аутентификацию по ключам; REST API между системами банка должен быть защищён (HTTPS, внутренняя сеть). |
| 3 | Отказоустойчивость: при недоступности сервиса ставок система кол-центра должна использовать последние полученные данные (кэш). |
| 4 | Простота интеграции для партнёра: формат файла — CSV с фиксированной структурой, разделитель — точка с запятой. |
| 5 | Масштабируемость: сервис депозитных ставок уже спроектирован горизонтально масштабируемым, что покрывает нагрузку от новых потребителей. |
| 6 | Использовать существующие технологии: Java/Spring Boot для доработок сервиса ставок, SFTP-сервер на базе Linux. |

### <a name="_qmphm5d6rvi3"></a>**Решение**
1. Единый источник ставок – сервис депозитных ставок (deposit-service), является централизованным хранилищем ставок (MS SQL). Это позволяет избежать дублирования и несогласованности данных.
2. Интеграция с внутренним кол-центром через REST API – самый быстрый и технологичный способ. Система кол-центра написана на Java Spring Boot, как и deposit-service, поэтому интеграция проста. Ставки могут кэшироваться в БД кол-центра для отказоустойчивости
3. Передача файлов для партнёрского кол-центра – партнёр не готов принимать API, поэтому используем файловый обмен через SFTP. Это безопасно (шифрование канала, ключевая аутентификация) и привычно для многих внешних интеграций. Файл формируется в формате CSV, удобном для загрузки в любую систему.
4. Автоматизация генерации файла – в составе deposit-service добавлен компонент-генератор, который по расписанию создаёт файл и выгружает его на SFTP-сервер. Расписание можно настраивать.
5. Отказоустойчивость – в случае недоступности deposit-service система кол-центра отдаёт последние закэшированные ставки. Для кол-центра задержка обновления файла не критична.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Передавать ставки в кол-центр через файлы. Это замедлит обновление и усложнит процесс для внутренней системы, где возможна online-интеграция.
2. Хранить ставки в АБС и отдавать напрямую. АБС перегружена, нельзя нагружать прямыми запросами от кол-центра. Лучше использовать легковесный сервис.
3. Использовать email-рассылку файлов. Небезопасно и ненадёжно по сравнению с SFTP.

**Недостатки, ограничения, риски**

1. Задержка обновления файла. Согласовать допустимую периодичность (например, раз в сутки). Для MVP достаточно.
2. Необходимость мониторинга выгрузки файлов. Настроить алерты при сбоях генерации или отправки файла (логи deposit-service).
3. Возможное увеличение нагрузки на deposit-service. Сервис спроектирован с запасом, горизонтальное масштабирование решает проблему.
